# Security boundaries and limitations
**Enforced (tested):** Text-to-SQL policy + read-only role + masking (`docs/sql-security.md`); investigator DB role without labels/names; no code path that acts on accounts;
human approval and audit trail for case decisions; idempotent ingestion with bounded retries and dead-lettering; secrets only via environment; sanitized API errors with request ids;
same-origin dashboard proxy (no CORS exposure, no keys in browser); dependency versions pinned (`constraints.txt`, `package-lock.json`); `npm audit` reports 0 vulnerabilities (production and development dependencies).
**Access control (server-side, tested):** every data route requires an `X-API-Key`; keys carry a role (`viewer` reads, `analyst` also uses `/bi` and `/investigations`) and an identity that is what gets written to audit trails and decisions (request bodies cannot set it). With no `AUTH_KEYS` the API fails closed (503) unless `AUTH_DISABLED=true` is set explicitly for a local demo. `/health` and `/ready` are public; `/metrics` is public on the API port (not forwarded by the dashboard proxy).
**Identifier privacy:** one response filter pseudonymises customer, account and device identifiers (keyed HMAC) in every JSON response, including free text; analysts may add `reveal_ids=true` (audited). Identifiers are also pseudonymised before evidence reaches the LLM. Transaction ids are not treated as identifying.
**Not provided:** per-user login/SSO (the dashboard proxy holds one analyst key, so everyone using the dashboard shares that identity), key rotation/expiry, per-key rate limits (the in-memory limiter covers `/bi` only; enforce at a gateway),
rate limiting is in-memory per process (enforce at a gateway), TLS, secrets management, encryption at rest, backup/DR, regulatory compliance (GDPR, AML/SAR obligations), cloud hardening.
Development passwords (`finsight_dev_password`, `finsight_bi_dev_password`, `finsight_inv_dev_password`, `dev-only-mask-key-change-me`) are placeholders and must be changed outside local use.
Pseudonymisation is not anonymisation. Prompt-injection defences reduce, but do not eliminate, model risk; the hard boundaries are the database role, SQL policy and the absence of action tools.
